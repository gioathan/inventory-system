# Tech Debt / Known Shortcuts

Track anything done quick-and-dirty here the moment you do it — future you will not remember the context otherwise.

## Format
- **What:** the shortcut taken
- **Why:** why it was reasonable at the time
- **Fix later by:** what the proper fix looks like, and roughly when it matters

---

## [2026-07-26] Aspire dashboard using default/insecure local settings
- **What:** No auth hardening on the Aspire dashboard, default local URLs.
- **Why:** Local-only dev tool, not a security concern at this stage.
- **Fix later by:** N/A — this only matters if the dashboard is ever exposed beyond localhost, which it shouldn't be.

## [2026-08-08] Inventory.Api applies EF migrations at startup, gated on Development only
- **What:** `Program.cs` calls `db.Database.Migrate()` inside the `IsDevelopment()` block on every app startup, instead of running migrations as a separate step.
- **Why:** Convenient for local dev with Aspire — no manual `dotnet ef database update` step to remember, and it's gated so it can never run in a non-dev environment as written.
- **Fix later by:** Before any non-local deployment (step 10, containerize/k8s), replace with a proper migration step (EF Core migration bundle or a one-off job) run before the app starts, not from inside the app itself.

## [2026-08-08] NU1903 vulnerability warning on Microsoft.OpenApi 2.0.0 (transitive)
- **What:** `dotnet build` reports a known high-severity advisory (GHSA-v5pm-xwqc-g5wc) for Microsoft.OpenApi 2.0.0, pulled in transitively by the webapi template's OpenAPI support.
- **Why:** Not pinned deliberately — it's whatever version `dotnet new webapi` referenced; only matters for OpenAPI doc generation in dev, not a runtime attack surface for this stage.
- **Fix later by:** Check for an updated Microsoft.OpenApi package before this project is ever exposed beyond local dev; revisit alongside other services once more are scaffolded and dependency versions are audited together.

## [2026-08-08] Running `dotnet test` can kill a manually-running `dotnet run` AppHost's Postgres
- **What:** Aspire derives container names deterministically from the resource config (e.g. `postgres-uqkwxjbd`), not randomized per process. Running the Aspire.Hosting.Testing-based concurrency test while the AppHost was already running manually via `dotnet run` caused the test's teardown to stop the same-named Postgres container the manual instance depended on, killing its database out from under it (the API process itself stayed up, just lost its DB).
- **Why:** Not something we chose — it's how Aspire's local container naming/reuse behaves. Only surfaced because we happened to run tests while a manual dev session was also up.
- **Fix later by:** No real fix needed; just a habit to keep — stop any manually-running AppHost before running the test suite locally (or accept you'll need to restart it after). Worth double-checking whether this also affects CI if multiple test runs could ever overlap on the same machine.

## [2026-08-08] `dotnet ef migrations add` timing trap: build-then-generate ordering
- **What:** `dotnet ef migrations add` runs its own build *before* writing the new migration `.cs` files, so a prior `dotnet build` + a later `dotnet run --no-build` can end up running a DLL that predates the migration and silently has zero migrations compiled in (`Database.Migrate()` then does nothing — no error, just an empty `__EFMigrationsHistory` table and every query 500ing with "relation does not exist").
- **Why:** Genuinely non-obvious tool behavior, not a code mistake — caught it by running Catalog.Api standalone and reading its console output directly, since Aspire doesn't forward per-resource console output to the AppHost's own stdout.
- **Fix later by:** Nothing to fix in code; just a habit — always `dotnet build` the solution *after* generating a migration and before the next `dotnet run --no-build`, or don't use `--no-build` right after touching migrations.

## [2026-08-08] Integration tests share the dev Postgres data volume across runs
- **What:** `AppHost.cs`'s `postgres.WithDataVolume()` is the same code path used by both `dotnet run` (manual dev) and `Aspire.Hosting.Testing`'s `DistributedApplicationTestingBuilder` (tests), so they all persist to the same named volume. Tests that used fixed constant SKUs/barcodes (e.g. `"WIDGET-1"`, `"CATALOG-TEST-DUPLICATE-SKU"`) started failing on reruns once leftover rows existed from a prior run or from manual `curl` testing — not because the code was broken, but because the test data wasn't unique.
- **Why:** `WithDataVolume()` is the right call for local dev (don't lose stock data every restart), and wasn't written with test isolation in mind since the test project didn't exist yet when that line was added.
- **Fix later by:** Fixed the immediate issue by generating unique SKUs/barcodes per test run (`Guid.NewGuid()` suffixes) rather than hardcoded constants — sufficient for now. If this becomes a recurring pain as more tests are added, look at giving the AppHost a way to skip `WithDataVolume()` under `DistributedApplicationTestingBuilder` specifically (e.g. an execution-context check) so tests get a clean database every run instead of relying on unique data alone.

## [2026-08-09] Integration tests were timing out from running full stacks in parallel
- **What:** Each integration test spins up its own complete AppHost (Postgres + Redis + all four services) via Aspire.Hosting.Testing. xUnit runs different test classes in parallel by default, so once there were 6 test classes, up to 6 full stacks were starting simultaneously and starving each other's containers/processes past each test's 60s timeout — 3 tests failed with `TaskCanceledException`, not because the code was wrong.
- **Why:** Wasn't a problem with only 1-2 test classes; only surfaced once enough services/tests accumulated to make the parallel resource contention real.
- **Fix later by:** Added `xunit.runner.json` with `parallelizeTestCollections: false` so these full-stack tests run sequentially — slower total wall-clock time, but each test gets the machine to itself. If the suite keeps growing and sequential runtime becomes painful, consider sharing one AppHost instance across tests in a class (via `IClassFixture`) instead of spinning up a fresh one per test.

## [2026-08-09] gRPC clients need "https://", not the REST clients' "https+http://" scheme
- **What:** Copying the REST clients' `new Uri("https+http://catalog-api")` pattern into `AddGrpcClient` broke immediately with `System.InvalidOperationException: No address resolver configured for the scheme 'https+http'.` `GrpcChannel` inspects the URI scheme itself to pick a resolver before any HttpClientFactory handler runs, and doesn't recognize Aspire's compound "try https, fall back to http" scheme — only plain `HttpClient`-based calls understand it. Fixed by using `https://catalog-api` for the gRPC clients specifically; service discovery still resolves it correctly underneath since `AddGrpcClient` is built on the same `HttpClientFactory` pipeline.
- **Why:** Not documented anywhere obvious — found by hitting the actual `InvalidOperationException` at runtime and reasoning through where GrpcChannel vs HttpClient diverge in how they interpret the URI.
- **Fix later by:** N/A — this is just the correct pattern going forward for any future gRPC client added to the system.

## [2026-08-09] CreateItem's category_id/image_url aren't validated before Guid.Parse
- **What:** `CatalogGrpcServiceImpl.CreateItem` calls `Guid.Parse(request.CategoryId)` directly on the incoming string with no try/catch — a malformed value throws an unhandled `FormatException`, surfacing as a generic gRPC `INTERNAL` error rather than a clean `INVALID_ARGUMENT`.
- **Why:** Scan Gateway's intake flow only ever passes a real `Guid.ToString()` or omits the field entirely, so this can't happen through the one caller that exists today. Left unvalidated to keep the first cut of intake/restock focused.
- **Fix later by:** Wrap the parse in a try/catch mapping to `RpcException(StatusCode.InvalidArgument)` before any other caller (e.g. a future admin UI) can hit this with untrusted input.

## [2026-09-12] sessionReport revenue uses today's Catalog price, not the price at time of sale
- **What:** `Query.SessionReport` multiplies a session's `Sold` quantity by whatever `CatalogApiClient.GetAllItemsAsync` returns *right now* for that Sku's price. If the price changed after the movements in that session happened, the reported revenue for that historical session will silently drift from what was actually charged at the time.
- **Why:** Catalog has no price history — `Item` stores one current `Price`, full stop. Snapshotting price per-movement would mean adding a `Price` column to `StockMovement`, which means Inventory would need to know price at write time, which crosses the "Inventory never knows money" boundary the whole ledger/reporting split was built around (see architecture.md). Not worth doing until this project actually needs to survive a price change occurring inside an already-closed session's window.
- **Fix later by:** If/when this matters: have Scan Gateway pass the price it already fetched from Catalog (during the scan/receive call) through to Inventory's `ReceiveStockAsync`/`/adjust` calls purely as an opaque snapshot value stored on the `StockMovement` row — Inventory still never *interprets* it, just carries it for Dashboard's report to read back instead of re-fetching current price.

## [2026-09-12] RestockSession is a single global lock, not per-item or per-category
- **What:** Only one `RestockSession` can be open system-wide at a time (enforced by a partial unique index on `ClosedAt IS NULL`). Two admins can't run independent restocking sessions concurrently, even for unrelated categories.
- **Why:** Matches the actual usage pattern described when this was designed — one admin, one restocking period, 2-3 days at a time — so a single global session was the simplest thing that fit. Also sidesteps having to decide how movements should be tagged if sessions could overlap.
- **Fix later by:** N/A unless multiple people start restocking concurrently; if that happens, the likely fix is scoping sessions by a category or location tag rather than making them fully independent per-Sku.

## [2026-09-13] `dotnet run --no-launch-profile` on the AppHost breaks all inter-service gRPC calls
- **What:** Running the AppHost with `dotnet run --no-launch-profile` makes Aspire bind every project resource to a single HTTP-only port instead of the usual HTTP+HTTPS pair. Every gRPC client (`AddGrpcClient<...>(o => o.Address = new Uri("https://catalog-api"))`) still insists on HTTPS, so any cross-service call (Scan Gateway → Catalog, Dashboard → Inventory) hangs waiting on a TLS handshake against a port that's only ever speaking plain HTTP — no error, no timeout from the server side, just silence until the caller's own client-side timeout eventually fires. REST-only endpoints (health checks, anything not calling another service) work fine, which made this confusing to isolate: the service is "up," just selectively broken.
- **Why:** `--no-launch-profile` was used during earlier debugging (started as a way to avoid `launchBrowser: true` opening a browser window in a headless session) without realizing it also drops the AppHost's own environment variables (`ASPIRE_DASHBOARD_OTLP_ENDPOINT_URL` etc. from `Properties/launchSettings.json`'s `https` profile), which is apparently what Aspire uses to decide whether to give child resources dual-scheme endpoints at all.
- **Fix later by:** N/A — just don't use `--no-launch-profile` when running the AppHost locally. Plain `dotnet run` (using the default `https` profile) is correct and was confirmed to give every project resource real HTTP+HTTPS endpoints, at which point every gRPC-dependent flow (category creation, item lookup, session summaries) works immediately with no code changes.

## [2026-09-13] `UseHttpsRedirection()` strips the Authorization header, silently breaking bearer auth
- **What:** Adding JWT auth broke every REST/gRPC call in the integration suite with 401s even though the client was sending a valid `Authorization: Bearer <token>` header. `UseHttpsRedirection()` issues a 307/308 redirect for any request hitting the plain-HTTP port, and .NET's `HttpClient` deliberately strips the `Authorization` header when it automatically follows a cross-scheme (http→https) redirect — a documented security behavior, not a bug in `HttpClient`. Diagnosed by confirming the header arrived empty server-side despite being set client-side, then confirming a request straight to the HTTPS port (no redirect involved) returned 200 with the same token.
- **Why:** Every service already binds both HTTP and HTTPS side-by-side via Kestrel (`launchSettings.json`), so the redirect was never adding real protection locally — it was just quietly breaking any caller that happened to hit the HTTP port first (which `Aspire.Hosting.Testing`'s `CreateHttpClient` does by default via service discovery).
- **Fix later by:** Nothing to fix — `UseHttpsRedirection()` was removed entirely from all 6 services. If this is ever deployed somewhere HTTP must be rejected outright (rather than upgraded), do it at the reverse proxy/ingress instead of in-process, where it won't touch application-level headers on a redirect it issues to its own callers.

## [2026-09-13] Corrupted Wolverine node-tracking row made Inventory.Api fail to start, looked exactly like an auth bug
- **What:** After the JWT rollout, `DashboardQueryTests` and `ScanCachingTests` hung/failed with `TaskCanceledException`/500s that looked auth-related (redirect handler in the stack trace, right after adding bearer-token forwarding). The real cause: Inventory.Api was crashing on startup with `Wolverine.Postgresql.PostgresqlNodePersistence.LoadNodeAgentStateAsync` throwing `KeyNotFoundException` on a stale node-agent row in its Postgres-backed durability store — left over from earlier ungraceful AppHost kills during this same debugging session. Since `postgres.WithDataVolume()` persists across restarts (see the 2026-08-08 entry on shared volumes), the corrupted row survived every subsequent `dotnet run`/`dotnet test`. Inventory.Api never opened its port; every test that called it just hung until its own timeout, which read exactly like a hung/misconfigured auth call.
- **Why:** Confirmed by running Inventory.Api standalone (`dotnet run --no-build`, pointed at the real Aspire-managed Postgres/RabbitMQ containers via their host-exposed ports) instead of through the full Aspire test harness — reproduces the exact unhandled exception in seconds instead of waiting out a 2-minute test timeout to see a generic `TaskCanceledException`.
- **Fix later by:** Nothing to fix in code — wiped the stale `...-postgres-data` Docker volume once to clear it. Worth remembering as a diagnostic: if a service's port never opens under Aspire (silent to the AppHost console, since it doesn't forward child stdout) after a run that involved killing the AppHost mid-test, suspect corrupted state in a `WithDataVolume()`-backed container before chasing the symptom that surfaced it.

## [2026-09-20] Kestrel needs two separate ports to serve gRPC and plain HTTP without TLS
- **What:** First attempt at running Catalog.Api's container in Kubernetes set `Kestrel__EndpointDefaults__Protocols=Http1AndHttp2` on its one HTTP port, expecting that to enable gRPC. Instead Kestrel logged `HTTP/2 is not enabled ... TLS is not enabled ... Connections to this endpoint will use HTTP/1.1` and every gRPC call failed. Without TLS there's no ALPN, and ALPN is what negotiates HTTP/1.1 vs HTTP/2 per-connection — `Http1AndHttp2` on a plain-HTTP endpoint just falls back to HTTP/1.1-only. Getting real cleartext HTTP/2 ("h2c") requires an endpoint pinned to `Http2` exclusively, which then can't also serve a kubelet `httpGet` probe (the probe's HTTP client doesn't speak HTTP/2 prior-knowledge).
- **Why:** Aspire never surfaces this because it always binds an HTTPS endpoint too, and TLS is exactly what makes ALPN (and therefore one port serving both protocols) possible — this only shows up once a service runs with no TLS at all, which local Aspire dev never does but a bare-bones k8s manifest does.
- **Fix later by:** Nothing to fix — this is the correct shape going forward: two named Kestrel endpoints (`Kestrel__Endpoints__Grpc__Url`/`Protocols=Http2` for gRPC traffic, `Kestrel__Endpoints__Http__Url`/`Protocols=Http1` for health probes), set entirely via env vars/config with no code changes. Also remember to clear the base container image's baked-in `ASPNETCORE_HTTP_PORTS=8080` — it binds its own default endpoint on the same port as the first named one otherwise and crashes on startup. See `k8s/catalog-api.yaml`.

## [2026-09-20] `postgres:18`'s Docker image changed its expected volume mount path
- **What:** A plain `postgres:18.3` Deployment with a PVC mounted at the traditional `/var/lib/postgresql/data` refused to start: `there appears to be PostgreSQL data in: /var/lib/postgresql/data (unused mount/volume)`. Postgres 18's docker image switched to expecting a single mount at `/var/lib/postgresql` (letting Postgres itself create a version-specific subdirectory inside it, in support of `pg_upgrade --link`), and treats the old-style path as leftover cruft rather than as the real data directory.
- **Why:** Not a Kubernetes/k3d-specific issue — this is purely the image's own breaking change between major versions; would hit the same way in `docker run` directly. Only surfaced now because this is the first time a Postgres container was hand-written from scratch rather than let Aspire's `AddPostgres` manage image/volume wiring.
- **Fix later by:** Nothing to fix — mount the PVC at `/var/lib/postgresql` (no `subPath`) for any `postgres:18+` container going forward. Also worth remembering: if a PVC has already been initialized once with the wrong layout (or with different `POSTGRES_HOST_AUTH_METHOD`/password settings), the container skips `initdb` on every subsequent start and just keeps re-running the earlier config — the fix is deleting the PVC and reapplying, not just fixing the manifest.

## [2026-09-20] `GrpcChannel` refuses to send bearer tokens over an insecure channel
- **What:** Rolling the k8s manifests out to Scan Gateway/Dashboard, every gRPC call they made to Catalog/Inventory failed with `System.InvalidOperationException: Call credential configured for gRPC client '...' requires TLS, and the client isn't configured to use TLS.` `AddCallCredentials` (used to forward the caller's bearer token — see the Staff/Auth & JWT section) refuses by default to attach credentials to a channel it considers insecure, as a safeguard against leaking a token to an unintended plaintext endpoint.
- **Why:** Never surfaced under Aspire because every gRPC client there talks to a real HTTPS endpoint. Once Catalog/Inventory's gRPC ports became plain HTTP/2 (h2c) in Kubernetes (see the entry above — no TLS/mTLS until Step 11), the exact same `AddCallCredentials` call started tripping this safeguard.
- **Fix later by:** Nothing to fix — added `.ConfigureChannel(o => o.UnsafeUseInsecureChannelCallCredentials = true)` on both gRPC client registrations in `ScanGateway.Api`/`Dashboard.Api`'s `Program.cs`. It's a no-op for the Aspire/HTTPS case (the flag only matters for an insecure channel), so one unconditional change covers both environments. **Correction (2026-09-22):** this entry originally predicted the flag would become unnecessary once Step 11 added mTLS. Verified false — see the Linkerd entry below for why.

## [2026-09-20] Kubernetes has no equivalent of Aspire's `WaitFor()`
- **What:** On first boot of the full k8s manifest set, `inventory-api`/`staff-api`/`notification-api` each restarted once (`RESTARTS: 1`) before settling into a stable `Running` state. `inventory-api`'s previous-container log showed Wolverine failing to connect to RabbitMQ and retrying; the underlying cause is that a plain `Deployment` has no primitive for "don't start until this other Service is actually accepting connections" — Kubernetes schedules and starts pods independently, unlike Aspire's explicit `.WaitFor(dependency)` calls in `AppHost.cs`.
- **Why:** Each dependent library's own retry/backoff (Wolverine's RabbitMQ connection retry, Npgsql's) happened to be enough to self-heal on the automatic restart — genuinely fine for this project's current scale, but not something to rely on if a dependency takes meaningfully longer to become ready than one restart cycle allows.
- **Fix later by:** N/A for now — if this ever becomes flaky (e.g. adding more services with slower-starting dependencies), the standard fixes are an `initContainer` that polls the dependency's readiness before the main container starts, or moving to a Helm chart with explicit dependency ordering/hooks.

## [2026-09-22] Linkerd's mTLS is invisible to the application — `UnsafeUseInsecureChannelCallCredentials` still needed
- **What:** After installing Linkerd (`linkerd install` + `linkerd viz install`, namespace annotated `linkerd.io/inject: enabled`), tested the hypothesis that real mTLS between pods would let `UnsafeUseInsecureChannelCallCredentials` be removed from Scan Gateway/Dashboard's gRPC clients. Removed it, rebuilt, redeployed: identical `InvalidOperationException` as before mTLS existed. `linkerd viz edges` confirms the actual connection between the two pods genuinely is `SECURED: √` — the encryption is real — yet .NET still refuses.
- **Why:** Linkerd's sidecar (`linkerd-proxy`) intercepts traffic transparently via iptables rules inside the Pod's network namespace, *underneath* the application. From the app's own perspective it's still dialing plain `http://catalog-api`; `GrpcChannel` decides whether a channel is "secure" purely from the URI scheme it was configured with at startup, with no way to observe that iptables is about to re-route the packet through an encrypted tunnel to the destination's sidecar. The mesh adds a real, meaningful protection (a compromised node/network tap can't read pod-to-pod traffic) but it's a different threat model than "did this process negotiate TLS," and doesn't change what the process itself sees.
- **Fix later by:** N/A — `UnsafeUseInsecureChannelCallCredentials = true` is correct and permanent here, mesh or no mesh, as long as the gRPC clients are configured with `http://` addresses. The only way to remove it would be making the *application* actually speak TLS (e.g. Linkerd's opaque-vs-TLS-terminating modes, or the app trusting Linkerd's own issued certs directly) — meaningfully more setup than this project needs right now.

## [2026-09-22] `host.docker.internal` goes stale after a network change, breaking `kubectl`
- **What:** Twice now, returning to this project after time away (different Wi-Fi network / VPN state) left `kubectl` hanging or failing with `dial tcp <stale-ip>:<port>: ... failed to respond`, even though the k3d containers were still up and healthy (`docker ps` showed them running for days). The kubeconfig's server URL uses `host.docker.internal`, which Docker Desktop resolves to a cached IP that doesn't get refreshed when the host's own IP changes.
- **Why:** First occurrence was fixed by a full Docker Desktop + `wsl --shutdown` restart (disruptive — drops every container). Second occurrence: confirmed the API server was actually reachable fine on `127.0.0.1:<port>` the whole time (`docker port k3d-inventory-system-serverlb` showed it published on `0.0.0.0`), meaning only the `host.docker.internal` DNS entry was stale, not Docker itself.
- **Fix later by:** Nothing to fix in the project — when `kubectl` hangs after time away, try `kubectl config set-cluster k3d-inventory-system --server=https://127.0.0.1:<port>` (port from `docker port k3d-inventory-system-serverlb`) before reaching for a full Docker Desktop restart. Only fall back to `wsl --shutdown` + relaunch if `127.0.0.1` genuinely doesn't respond either.

## [2026-09-22] k3d node's internal IP flapped after 2+ days of uptime, causing intermittent `kubectl` TLS timeouts
- **What:** After the cluster had been running continuously for 2+ days (through the Linkerd install, which roughly doubled total container count via sidecar injection — ~49 containers in one Docker container acting as the k3s node), `kubectl` started failing intermittently with `net/http: TLS handshake timeout` — a different symptom from the `host.docker.internal` DNS-staleness entry above (that one fails instantly and consistently; this one was sporadic, sometimes working). The k3d node's own logs showed `"NodeIPs changed for the node"` firing repeatedly, flapping between two addresses on the Docker bridge network.
- **Why:** Root cause not fully isolated — plausibly some combination of extended uptime, the container-count increase from meshing every pod, and residual effects of the network changes/Docker restarts earlier in the same session. `docker stats` showed real but not extreme load (~38% CPU/memory) at the time, so this reads more like network-bridge degradation than pure resource exhaustion.
- **Fix later by:** Resolved by a full Docker Desktop + `wsl --shutdown` restart (same fix as the DNS-staleness entry, but this time actually necessary — the lighter kubeconfig-only fix doesn't help when the underlying node IP itself is unstable). If this recurs, check the k3d server node's own logs (`docker logs k3d-inventory-system-server-0 | grep "NodeIPs changed"`) to tell the two failure modes apart before picking a fix — a single IP that just isn't the one DNS points to vs. an IP that keeps changing are different problems with different remedies.

## [2026-09-22] Canary deploy: `catalog-api-v1`/`catalog-api-v2` behind a weighted `GRPCRoute`
- **What:** Added a second Deployment (`catalog-api-v2`, currently the identical image — see `k8s/catalog-api-canary.yaml`) and a Gateway API `GRPCRoute` that splits traffic between `catalog-api-v1`/`catalog-api-v2` by weight (80/20). The apex `catalog-api` Service was changed to have a selector matching no real pods (`version: does-not-exist`) — this is deliberate, not a bug: with the `GRPCRoute` applied, Linkerd's destination controller resolves "where does traffic for catalog-api go" from the route's weighted `backendRefs` instead of the Service's own endpoint list, so giving the apex Service real endpoints too would just be a second, conflicting source of truth.
- **Why:** Chose `GRPCRoute` over the more commonly-documented `HTTPRoute` since Catalog.Api is gRPC-only — `GRPCRoute` matches on gRPC service/method semantics rather than raw HTTP paths, a better fit for what's actually being routed. Chose Gateway API over Linkerd's older SMI `TrafficSplit` CRD since Linkerd dropped built-in `TrafficSplit` support in favor of Gateway API as of 2.15.
- **Fix later by:** N/A — this is the intended pattern going forward for any future canary rollout. The one trap: applying `catalog-api.yaml` (v1 + the selector-less apex Service) *without* also applying `catalog-api-canary.yaml` in the same breath leaves the apex Service with zero endpoints and nothing reaches catalog-api at all until the canary file is applied too, even to route 100% to v1.
